the first public `v0.1.0` release. Items are roughly in dependency order —
metadata and in-flight PRs first, then release machinery, then the tag and
publish.

Mark each `[x]` as it's done. Anything that gets bumped to v0.2 should be
moved to the corresponding section of `RELEASE_PLAN.md` with a one-line
rationale.

## Stage 2 — Crate metadata for crates.io

For every crate that will be published (`metaltile-core`,
`metaltile-macros`, `metaltile-codegen`, `metaltile-runtime`,
`metaltile-std`, `metaltile`), verify the `Cargo.toml` has:

- [ ] `description` — one-sentence, non-empty, distinct per crate.
- [ ] `repository` — points at the canonical URL chosen in Stage 0.
- [ ] `homepage` — same URL or a project page; not empty.
- [ ] `license = "Apache-2.0"` (matches root `LICENSE`).
- [ ] `keywords` — up to 5; include `metal`, `gpu`, `apple`, `dsl`,
      `kernels` or similar.
- [ ] `categories` — up to 5; pick from `crates.io/category_slugs`
      (e.g. `hardware-support`, `compilers`, `development-tools`).
- [ ] `readme` — points at the per-crate README added in PR #18.
- [ ] `rust-version` — either pinned to the nightly date the
      `rust-toolchain.toml` already specifies, or omitted with a doc
      comment in CONTRIBUTING explaining the nightly policy.
- [ ] Crate version is `0.1.0` and no internal deps use `*` or `>=` — every
      workspace-internal dep is pinned to `= 0.1.0`.

Then on a clean clone:

- [ ] `cargo publish --dry-run -p metaltile-core` succeeds.
- [ ] Same for `-p metaltile-macros`, `-p metaltile-codegen`,
      `-p metaltile-runtime`, `-p metaltile-std`, `-p metaltile`.

`metaltile-cli` stays `publish = false` for v0.1.0 — it ships as a binary
on the GitHub Release page only. Re-evaluate for v0.2.0.

## Stage 3 — Documentation pass

- [ ] **README.md**: confirm the "Early development — APIs are not yet
      stable" line is present and prominent. Update the install snippet to
      reference the published `metaltile = "0.1"` line (which will work
      after Stage 5 publish). Verify every link resolves.
- [ ] **README.md performance section**: confirm the headline number
      (~110% of MLX on M4 Max average) matches the baseline JSON shipped at
      the release SHA. Add a one-paragraph "Known regressions" callout that
      names the M5 Max SDPA+GQA+bf16 (31% MLX) and softmax bf16 (29% MLX)
      cells and links to `baselines/README.md`.
- [ ] **CONTRIBUTING.md**: confirm the release process described
      (`dev → main` PR, tag, `gh release`) is what we will actually do.
      If we automate publishing via a workflow as part of this cut,
      document the workflow here.
- [ ] **CHANGELOG.md** (new file at repo root). Populate a single
      `## v0.1.0 — YYYY-MM-DD` section. Group entries under headings:
      *Features*, *Performance*, *Codegen*, *Runtime*, *CLI*, *Docs / CI*.
      Keep entries short — one line per merged PR, referencing PR numbers.
      The 27-PR merge window in `IN_FLIGHT.md` is the source list.
- [ ] **No AI trailers anywhere** — repo CI fails any commit/PR body
      containing `Co-Authored-By` lines or AI-platform names. This applies
      to the CHANGELOG, release notes, and the release commit message.
      Run a final `git log v0.1.0 -- | grep -iE 'co-authored|claude|gpt|copilot'`
      sanity check before tagging.

## Stage 4 — Release machinery dry run

- [ ] On a fresh clone of `dev` at the candidate SHA, run
      `cargo test --workspace`, `make clippy`, `make typos`, `make fmt-check`.
      All must pass.
- [ ] Run the macOS kernels job (`tile bench -vv`) and confirm 241/241

      against the previous M4 Max / M5 Max baselines.
- [ ] Refresh `baselines/apple-m4-max.json` and `baselines/apple-m5-max.json`

      `cargo build --release -p metaltile-cli` and confirm the binary runs

## Stage 5 — Tag, publish, announce

- [ ] Merge the `dev → main` PR. `main` is now at the v0.1.0 candidate SHA.
- [ ] `git tag -a v0.1.0 -m "metaltile v0.1.0"` on `main`. Push the tag.
- [ ] Publish to `crates.io` in dependency order, one at a time, checking
      that `cargo search` shows the new version before publishing the next:
      `metaltile-core` → `metaltile-macros` → `metaltile-codegen` →
      `metaltile-runtime` → `metaltile-std` → `metaltile`.
- [ ] `gh release create v0.1.0 --notes-file <(awk '/## v0.1.0/,/## /'
      CHANGELOG.md)` (or hand-curated notes). Attach the prebuilt `tile`
      binary as a release asset.
- [ ] **Reproducer smoke test on a clean macOS box**:
      `cargo install metaltile-cli@0.1.0` *(if a separate path exists for
      v0.1; otherwise document `cargo install --git ... --tag v0.1.0
      -p metaltile-cli`)*, then `tile bench --filter rms_norm_per_head`,
      then visually confirm a row matches a cell in the shipped baseline
      JSON. Paste the transcript into the release notes.

## What to do if the cut slips

If any v0.1-scope PR breaks the release at the last minute, **drop it from
v0.1.0** rather than holding the tag. The release plan is deliberately built
so any individual PR is removable — the headline value of v0.1.0 is
"taggable, installable, honest about its limits," not any specific feature.
A first patch release (`v0.1.1`) can pick up anything that misses.
